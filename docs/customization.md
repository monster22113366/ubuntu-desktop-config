# 配置定制规范

## 1. 目的

本文档规定 ubuntu-desktop-config 工程中各类配置参数的归属、组织方式和修改原则。

目标是：

- 让用户能够快速找到需要修改的参数。
- 避免相同参数散落在多个文件中。
- 保持软件模块之间的低耦合。
- 方便 Codex 和 ChatGPT 理解工程并协助移植。
- 让配置修改具有明确的验证和回滚路径。

## 2. 配置分类

工程中的配置分为三类。

### 2.1 硬件配置（Hardware Profile）

文件：

`profiles/hardware.lua`

用于保存与具体设备相关的参数。

| 参数 | 示例 |
|---|---|
| 显示器名称 | eDP-1、DP-4 |
| 显示器分辨率 | 2560x1600 |
| 刷新率 | 165Hz |
| 显示器位置 | 0x0、2560x0 |
| 缩放比例 | 1.0 |
| 网络接口名称 | wlp8s0 |
| 电池设备名称 | BAT1 |
| 背光设备名称 | nvidia_wmi_ec_backlight |
| 特定硬件参数 | 根据实际设备定义 |

原则：

1. 只保存确实与硬件有关的参数。
2. 不强制自动检测所有硬件。
3. 不同硬件之间存在差异时，提供明确的修改入口。
4. 不将软件外观和个人偏好混入硬件配置。

### 2.2 用户配置（User Profile）

文件：

`profiles/user.lua`

用于保存个人偏好。

| 参数 | 示例 |
|---|---|
| 主题 | Tokyo Night Storm |
| 窗口间距 | 5 |
| 外部间距 | 10 |
| 窗口圆角 | 10 |
| 边框宽度 | 2 |
| 窗口透明度 | 0.96 |
| 动画开关 | true |
| 快捷键偏好 | Alt+Tab |

原则：

1. 只保存用户主动选择的偏好。
2. 不保存特定硬件的设备标识。
3. 不强制所有软件使用相同的配置接口。
4. 单个软件独有的设置可以留在对应软件模块中。

### 2.3 模块配置（Module Configuration）

位置：

`config/<application>/`

用于保存各软件的具体实现配置。

例如：

| 软件 | 配置文件 |
|---|---|
| Hyprland | Lua 配置 |
| Waybar | JSONC、CSS、Shell |
| Ghostty | Ghostty 原生配置 |
| Neovim | Lua 配置 |
| Yazi | TOML、Lua |
| Starship | TOML |

模块配置负责：

- 调用软件原生接口。
- 实现具体功能。
- 读取需要的硬件参数和用户偏好。
- 处理软件自身的特殊配置。

## 3. 参数归属判断

添加一个新参数时，按照以下规则判断。

### 3.1 是否与具体硬件有关？

如果更换电脑后通常需要修改，则优先考虑 Hardware Profile。

例如：

- 显示器型号和输出名称。
- 特定传感器路径。
- 电池设备标识。

### 3.2 是否属于用户主动选择的偏好？

如果更换电脑后仍然希望保持一致，则优先考虑 User Profile。

例如：

- 主题。
- 窗口圆角。
- 动画风格。
- 快捷键偏好。

### 3.3 是否只属于某个软件？

如果参数只对某个软件有意义，且没有跨模块共享需求，则直接放在对应模块中。

例如：

- Neovim 的补全插件配置。
- Waybar 的模块排列。
- Ghostty 的光标样式。

不要为了追求统一而将所有参数都抽取到 Profile。

## 4. 参数共享原则

### 4.1 单一事实来源

同一个共享参数原则上只定义一次。

例如，主题名称可以在 User Profile 中定义，而不同软件分别实现对应的配色。

### 4.2 避免重复抽象

如果某个参数只被一个模块使用，不必为了未来可能的复用而提前抽象。

### 4.3 保持原生格式

不同软件使用各自擅长的配置格式。

不建立强制统一的配置转换框架。

### 4.4 明确依赖关系

Profile 不依赖具体软件模块。

软件模块只读取自己需要的参数，不应依赖其他无关模块。

## 5. 硬件移植规范

移植到新设备时：

1. 检查设备型号、显卡、显示器、输入设备等硬件信息。
2. 确认目标系统和软件版本。
3. 修改 Hardware Profile。
4. 检查各软件模块是否存在设备专属配置。
5. 修改必要的模块配置。
6. 运行配置检查。
7. 进行实际运行验证。

不应为了适配新设备而无必要地重构通用模块。

## 6. 用户定制规范

用户希望改变桌面外观或操作习惯时：

1. 优先检查 User Profile。
2. 如果参数尚未抽象，则检查对应软件模块。
3. 判断是否有必要将共享参数提取到 User Profile。
4. 避免为了一个模块的特殊需求影响其他模块。

## 7. 配置变更验证

每次修改配置后，应尽可能执行对应的验证。

| 模块 | 验证方式 |
|---|---|
| Hyprland | `Hyprland --verify-config` |
| Waybar JSONC | `python3 -m json.tool`（适用于严格 JSON；JSONC 需使用支持 JSONC 的解析器） |
| Shell 脚本 | `bash -n` |
| Ghostty | 使用对应版本支持的配置检查方式 |
| Neovim | `nvim --headless` 加载检查 |
| Yazi | 使用对应版本支持的配置检查方式 |

语法验证不能替代实际运行验证。

## 8. 安全原则

1. 修改现有配置前先备份。
2. 不直接覆盖未知来源的用户配置。
3. 不将代理订阅、Token、密码等敏感信息提交到 Git。
4. 不在未经验证时批量部署配置。
5. 保留恢复原配置的能力。
