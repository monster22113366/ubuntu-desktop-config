## 10. 配置组织与模块依赖

### 10.1 设计原则

采用统一参数定义、分散模块实现的架构。

Hardware Profile 和 User Profile 负责保存参数，各软件模块自行决定如何读取和使用这些参数。

不建立强制统一的配置加载框架。

### 10.2 Hardware Profile

负责描述设备相关参数，例如：

- 显示器名称、分辨率、刷新率、位置和缩放比例。
- 硬件监控设备标识。
- 特定设备的功能参数。
- 必要的硬件兼容性设置。

不负责硬件自动检测，也不负责软件配置的生成和加载。

### 10.3 User Profile

负责描述用户偏好，例如：

- 主题选择。
- 窗口间距、圆角和边框。
- 动画偏好。
- 用户快捷键偏好。
- 应用程序的个性化选项。

不负责软件模块的具体实现。

### 10.4 软件模块

每个软件模块保持自身的原生配置格式和实现方式。

例如：

| 软件 | 原生配置格式 |
|---|---|
| Hyprland | Lua（当前使用的 Lua 配置接口） |
| Waybar | JSONC、CSS、Shell |
| Ghostty | Key-value 配置 |
| Neovim | Lua |
| Yazi | TOML、Lua |
| Starship | TOML |

各模块仅在确实需要时读取 Profile 参数。

如果某个参数只与单个软件有关，也可以直接保留在该软件的配置中，不必强行抽象到 Profile。

### 10.5 模块依赖原则

1. Profile 不依赖任何软件模块。
2. 软件模块可以读取 Profile，但不应反向依赖其他无关模块。
3. 不同软件之间尽量保持独立。
4. 共享参数应有明确的归属。
5. 不为统一形式而引入不必要的转换层和抽象层。

### 10.6 配置修改与移植

迁移到新设备时：

1. 检查目标设备的硬件和软件环境。
2. 修改 Hardware Profile 中与设备有关的参数。
3. 修改 User Profile 中需要调整的个人偏好。
4. 检查各软件模块是否存在设备相关配置。
5. 验证配置并进行部署。

迁移过程中优先修改参数，不随意改变通用模块的结构。
